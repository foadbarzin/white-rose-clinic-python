## ۱) قابلیت‌های ساخته‌شده

### احراز هویت
- ورود با نام کاربری/رمز، خروج، خروج از همه دستگاه‌ها، `auth.me`، فهرست نشست‌های فعال.
- تغییر رمز توسط کاربر (با رمز فعلی) و بازنشانی توسط مدیر با **الزام تغییر در ورود بعدی**.
- پیام خطای یکسان برای «کاربر ناموجود» و «رمز اشتباه» + هش ساختگی برای یکسان‌سازی زمان پاسخ.
- قفل حساب پس از ۵ تلاش ناموفق به مدت ۱۵ دقیقه + محدودیت نرخ ورود (۱۰/دقیقه بر IP و نام کاربری).
- جلوگیری از Session Fixation: توکن فقط سمت سرور تولید و یک‌بار تحویل می‌شود.

### نشست
- توکن تصادفی ۲۵۶ بیتی (`secrets.token_urlsafe`)، ذخیرهٔ فقط `SHA-256` در `user_sessions.token_hash`.
- انقضای بی‌کاری **۳۰ دقیقه** (sliding، throttle ۶۰ ثانیه) و عمر مطلق **۱۲ ساعت**.
- حداکثر ۳ نشست فعال؛ ابطال فوری توسط مدیر؛ رد استفادهٔ مجدد از توکن ابطال‌شده/منقضی با پیام فارسی.
- ابطال همهٔ نشست‌ها در تغییر/بازنشانی رمز و غیرفعال‌سازی کاربر.

### کاربران
- ایجاد (نام کاربری یکتا، اعتبارسنجی رمز، نقش‌های چندگانه)، ویرایش، فعال/غیرفعال، قفل/بازکردن.
- مشاهدهٔ نشست‌ها و ابطال تک/همه، تاریخچهٔ فعالیت امنیتی، بازنشانی رمز.
- حذف کاربر وجود ندارد (سوابق حفظ می‌شود)؛ غیرفعال‌سازی آخرین دارندهٔ `rbac.manage` و همچنین عملیات روی حساب خود ممنوع است.

### RBAC
- سه موجودیت مستقل: Users، Roles، Permissions.
- کاتالوگ **۳۲ مجوز** در کد با ماژول و توضیح فارسی؛ نقش‌ها در DB؛ چند نقش برای هر کاربر.
- مجوز مؤثر = اجتماع مجوزهای نقش‌های فعال؛ کنترل در Backend برای هر اکشن.
- ایجاد/ویرایش نقش، تخصیص/حذف نقش، تخصیص/حذف مجوز.
- **ضد ارتقای دسترسی:** واگذاری فقط برای زیرمجموعهٔ مجوزهای عامل؛ تغییر نقش خود ممنوع؛ نقش سیستمی `owner` محافظت‌شده.

### Audit Log
- ثبت ساخت‌یافته: شناسه، زمان (UTC، نمایش Asia/Tehran)، کاربر عامل، نوع رویداد، موجودیت/شناسه، نتیجه، IP، User-Agent، Correlation ID و جزئیات غیرحساس.
- رویدادها: ورود موفق/ناموفق/قفل/نرخ، خروج، خروج همه، انقضای نشست، ابطال نشست، تغییر/بازنشانی رمز، ایجاد/ویرایش/غیرفعال‌سازی/فعال‌سازی/بازکردن قفل کاربر، ایجاد/ویرایش نقش، تخصیص/حذف نقش و مجوز، Bootstrap، رد مجوز.
- زنجیرهٔ هش `hash_prev → hash_self` با زمان یکنوای یکتا و تابع `verify_chain`.
- بدون هیچ API برای ویرایش/حذف؛ فیلتر و مشاهده با مجوز `audit.read`.

### رابط فعلی (تغییرات حداقلی)
- نمایش نسخهٔ ۰.۶.۰ از سرور (`window.WRC_APP_VERSION`).
- مدیریت نشست: پیام انقضا و بازگشت به صفحهٔ ورود، دکمهٔ «خروج از همه دستگاه‌ها».
- صفحهٔ کاربران بازنویسی افزایشی: نقش‌ها، وضعیت/قفل/نشست، بازنشانی رمز، فعال/غیرفعال، بازکردن قفل، فعالیت.
- مسیرهای جدید «دسترسی‌ها → نقش‌ها و مجوزها» و «گزارش رویدادها» با همان کلاس‌های ظاهری و RTL.
- فرم Bootstrap عمومی از صفحهٔ ورود حذف شد (راه‌اندازی فقط CLI).
- ظاهر، رنگ‌ها، فونت، RTL و تمام مسیرهای قبلی حفظ شدند.

## ۲) ساختار دیتابیس (مهاجرت `a4576410fc23`)

نسخهٔ اسکیما پس از فاز ۳: **۳۱ جدول** در `Base.metadata` (۳۲ با `alembic_version`).

| جدول | نقش |
|---|---|
| `roles` | نقش‌های قابل تعریف، `is_system` برای `owner`، `legacy_role` فقط برای منو |
| `role_permissions` | PK مرکب (`role_id`, `permission_code`)؛ کد باید در کاتالوگ باشد |
| `user_roles` | PK مرکب (`user_id`, `role_id`)؛ چند نقش برای هر کاربر |
| `user_sessions` | + `ip_address`, `user_agent` |
| `audit_log` | + `ip_address`, `user_agent`؛ زنجیرهٔ هش |

- مهاجرت فقط DDL است: **هیچ نقش/کاربر/مجوز تخصیص‌یافته‌ای** ساخته نمی‌شود.
- `users.role` حفظ شد اما فقط projection نمایشی است؛ مبنای مجوز، `user_roles` است.

## ۳) اکشن‌های API (پیاده‌شده)

`users.list`, `users.get`, `users.create`, `users.update`, `users.disable`, `users.enable`, `users.unlock`,
`users.change_password`, `users.sessions`, `users.revoke_sessions`, `users.activity`,
`roles.list`, `roles.create`, `roles.update`, `roles.assign`, `roles.revoke`,
`permissions.list`, `permissions.assign`, `permissions.revoke`, `audit.list`, `audit.get`.

- سایر اکشن‌ها پس از احراز هویت `ACTION_NOT_IMPLEMENTED` می‌دهند (هیچ عملیات مالی در این فاز نیست).
- اسکیمای هر اکشن با Pydantic (`extra="forbid"`) اعتبارسنجی می‌شود؛ خطاها مقادیر حساس را بازنمی‌تابانند.

## ۴) مدل امنیتی (خلاصه اجرایی)

| موضوع | تصمیم اجراشده |

| ابطال | خروج، خروج همه، تغییر رمز، غیرفعال‌سازی، ابطال مدیر؛ استفادهٔ مجدد رد می‌شود |

| Audit | فقط-افزودنی، زنجیرهٔ هش، بدون API ویرایش/حذف، ماسک کلیدهای حساس |

| Bootstrap | فقط CLI با `--confirm`، بدون رمز پیش‌فرض، یک‌بارمصرف |

## ۷) روش راه‌اندازی اولیهٔ امن (Bootstrap)

```powershell
$env:PYTHONPATH = "backend"
python -m app.cli bootstrap-owner --username owner --generate-password --confirm
```

- **خارج از API عمومی**: اکشن `setup.bootstrapAdmin` عمداً `ACTION_NOT_IMPLEMENTED` است.
- **بدون رمز پیش‌فرض**: رمز یا تولید تصادفی می‌شود (فقط یک‌بار نمایش) یا از `--password-stdin`.
- **یک‌بارمصرف**: اگر هر کاربر فعالی وجود داشته باشد، اجرا مسدود است.
- نقش سیستمی `owner` با تمام ۳۲ مجوز ساخته می‌شود و قابل ویرایش/کاهش نیست.
- حساب با `must_change_password=true` ساخته می‌شود؛ تا تغییر رمز فقط اکشن‌های نشست مجازند.
- بررسی وضعیت بدون افشای اطلاعات: `python -m app.cli status`.

## ۹) وضعیت Git

| مورد | مقدار |
|---|---|
| مخزن محلی | `white-rose-clinic-migration` (مستقل، بدون Remote) |
| شاخهٔ کار | `migration/python-foundation` |
| شاخهٔ اصلی | `main` (به‌روزرسانی Fast-forward از شاخهٔ کار) |
| تاریخچه | `f9de12f` (اسناد فاز ۱) → `ea60d61` (بنیاد فاز ۲) → `feat(auth): phase 3 authentication users rbac and audit` |
| Remote | **تنظیم نشد / Push انجام نشد** |

**دلیل عدم انتشار:** آدرس Remote اعلام‌شده در دستور (`https://github.com/foadbarzin/white-rose-clinic.git`) دقیقاً همان `origin` **پروژهٔ اصلی ۰.۴.۳** است (با `git remote -v` در پروژهٔ مرجع تأیید شد). Push به آن، تاریخچهٔ پروژهٔ قدیمی را تغییر می‌دهد و با الزام «پروژهٔ ۰.۴.۳ کاملاً دست‌نخورده بماند» و «اگر Remote/شاخهٔ مقصد نامطمئن است Push نکن» در تعارض است. بنابراین Push انجام نشد و برای انتشار امن یکی از دو مسیر لازم است:

1. ساخت مخزن مستقل (مثلاً `white-rose-clinic-migration`) و دادن URL آن، یا
2. اجازهٔ صریح و مکتوب برای افزودن شاخهٔ جدا در مخزن قدیمی (بدون دست‌زدن به `main` قدیمی).

پس از تعیین Remote، انتشار با دستور زیر (بدون Force) انجام می‌شود:

```powershell
git remote add origin <MIGRATION_REPO_URL>
git push -u origin main
```
